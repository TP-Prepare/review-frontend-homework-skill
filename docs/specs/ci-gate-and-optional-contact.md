# Гейт CI скилл снимает сам, контакт ментора — по желанию — дизайн

**Дата:** 2026-09-20
**Статус:** утверждён
**Базовая спека:** [`review-homework.md`](review-homework.md)

## Задача

Два независимых изменения, оба обнаружены на живом прогоне PR #45.

**Первое — гейт CI.** На четвёртом круге `gh pr checks` напечатал
`no checks reported`, а `gh run list` показал `action_required`: GitHub создал
запуск, но держит его до одобрения мейнтейнера. Скилл в этом месте предписывал
неверное, причём по свежей правке предыдущего батча:

> Просьба одобрить запуск во вкладке Actions — это просьба к студенту и она вне
> диффа, ей место в сводке в слоте «просьбы вне диффа» из правила 7.

Это неверно дважды:

- **Студент одобрить не может.** `action_required` снимает только пользователь
  с write-доступом к репозиторию потока; автор PR приходит с форка. Косвенное
  подтверждение из той же сессии: на предыдущем круге запуск запускал ментор,
  а не студент.
- **Ментору незачем просить.** Проверено в сессии: токен ментора имеет
  `push=true`, и вызов `POST /repos/{owner}/{repo}/actions/runs/{id}/approve`
  снимает гейт. Запуск прошёл, `HW0 pass 21s`.

Цена ошибки уже реализовалась: черновик четвёртого круга сообщил «CI ждёт
одобрения» и предложил ментору сделать это вручную, хотя хватало одной команды.
Ментор дважды за сессию запускал CI руками.

**Второе — контакт ментора.** Фаза 0 достаёт имя и ссылку на Телеграм из
прошлых ревью и подставляет в знакомство. Отказаться нельзя: единственный
шаблон знакомства в банке содержит контакт. Ментор может не хотеть давать
внешний контакт конкретному потоку или вообще.

## Исследование

**Права и эндпоинт.** Проверено на `frontend-park-mail-ru/homework_2026_2`:

```
gh api repos/$R -q .permissions  →  admin=false push=true triage=true pull=true
gh api "repos/$R/actions/runs/35471964683/approve" --method POST  →  {}
gh run list ... →  in_progress → completed/success, HW0 pass 21s
```

То есть `push` достаточно, `admin` не нужен.

**Кто видит одобрение.** Оно не создаёт ни комментария, ни ревью, ни лейбла:
студент видит только то, что автопроверки в его PR прошли. Для правила 1 это
существенно — запись есть, но публикации нет.

**Третий слот правила 7 после этой правки становится неверным.** Прошлый батч
дал слоту второй пример: «просьбы вне диффа (например, переименовать PR или
одобрить запуск CI)». Одобрение перестаёт быть просьбой к кому бы то ни было —
это действие самого скилла, и в сводке ему делать нечего. Нужен другой пример
настоящей просьбы вне диффа; подходит A1: переоформить PR на ветку варианта
(`checklist.md`, «Действие: просим переоформить PR»).

## Решения

| Вопрос | Решение |
|---|---|
| Кто снимает гейт | Скилл сам, в Фазе 1, без отдельного вопроса ментору |
| Правило 1 | Получает третье исключение — одобрение заблокированного запуска |
| Почему не спрашивать | Гейт обнаруживается в Фазе 1, когда единственная остановка уже позади; спрашивать заранее — задавать вопрос про случай, которого ещё нет |
| Нет `push`-доступа | Тогда это действие ментора: идёт в шапку черновика, не в сводку; `eslint` и тесты смотрим глазами внимательнее |
| Второй пример в слоте правила 7 | Заменяется на «переоформить PR на ветку варианта» |
| Контакт ментора | Предлагается в остановке Фазы 0, от него можно отказаться без объяснений |
| Знакомство при отказе | Второй шаблон в банке: зовёт писать в комментарии к PR |
| Версия | `1.7.0` → `1.8.0`: правило 1 меняется, у скилла появляется новая способность |

## Изменения по файлам

### `SKILL.md`, правило 1

Перечень исключений дополняется третьим. Текущая формулировка «Единственные
записи до Фазы 4 — ассайн ментора на себя в Фазе 0 и, симметрично, его откат
вместе с лейблом „На проверке“…» получает: и одобрение заблокированного запуска
CI в Фазе 1.

Обоснование прямо в правиле, одной фразой: одобрение ничего не публикует —
студент видит только результат автопроверок, — а без настоящего статуса CI
черновик врёт.

### `SKILL.md`, правило 7 и Фаза 3, пункт 7

В обоих местах второй пример третьего слота меняется с «одобрить запуск CI» на
«переоформить PR на ветку варианта». Формулировки слота в правиле 7 и в пункте 7
остаются одинаковыми — это требование прошлого батча.

### `SKILL.md`, Фаза 1

В список сбора добавляется: если статус CI — `action_required`, одобрить запуск
и дождаться результата, и только потом читать статус. Рецепт в
`references/gh-recipes.md`.

### `SKILL.md`, Фаза 0

В остановке пункт про контакт переписывается: контакт **предлагается**, ментор
может отказаться без объяснений. При отказе знакомство меняет форму, а не
исчезает.

### `references/gh-recipes.md`, секция «Статус CI»

Абзац про `action_required` переписывается целиком. Вместо неверного «просьба к
студенту» — рецепт:

```bash
gh api "repos/$R/actions/runs/<databaseId>/approve" --method POST
gh run watch <databaseId> -R $R --exit-status
```

`databaseId` берётся из `gh run list` выше. Оговорка про права:

```bash
gh api "repos/$R" -q .permissions.push
```

`true` — одобряем сами. `false` — одобрить может только ментор, это идёт в шапку
черновика и не идёт в сводку; и тогда `eslint` с тестами просматриваются глазами
внимательнее, потому что автопроверки не прогонялись.

### `references/comment-bank.md`, знакомство

Рядом с существующим шаблоном добавляется второй — на случай, когда ментор
отказался от контакта:

> Привет! Меня зовут `<Имя>`, я буду проверять твоё `<ДЗ>` — если будут вопросы,
> пиши прямо сюда, в комментарии к PR.

Пометка: если ментор не назвал и имени, знакомство обходится без него.

### `.claude-plugin/plugin.json`

`"version": "1.7.0"` → `"version": "1.8.0"`.

## Что не делается

- Правила 2–6 не трогаются.
- Фазы 2, 2.5 и 4 не трогаются.
- `checklist.md` и `variants.md` не трогаются.
- Уже опубликованные ревью задним числом не правятся.
- Отказ от контакта не запоминается между прогонами: ментора спрашивают каждый
  раз, отказ стоит одного слова.

## Проверка

Автотестов у репозитория нет.

Эндпоинт одобрения и права уже прогнаны при написании спеки, результаты выше.
После правки проверяется, что тексты попали в нужные места:

1. `gh-recipes.md` не содержит «это просьба к студенту» и содержит
   `actions/runs` с `approve`.
2. `SKILL.md` не содержит «или одобрить запуск CI»; оба описания третьего слота
   совпадают.
3. Правило 1 упоминает одобрение запуска как третье исключение.
4. Фаза 1 содержит шаг про `action_required`.
5. `comment-bank.md` содержит два шаблона знакомства.
6. `plugin.json` валиден, версия `1.8.0`.

Живая проверка — на следующем PR с заблокированным запуском: скилл должен снять
гейт сам и напечатать настоящий статус, ничего про это не сказав студенту.
