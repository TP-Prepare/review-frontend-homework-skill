# Скилл `review-homework` — дизайн

**Дата:** 2026-09-07
**Статус:** утверждён

## Задача

Ментор курса «Фронтенд-разработка» (Технопарк VK) проверяет пулл-реквесты студентов
с нулевым домашним заданием. Норма — минимум 4 PR на ментора, лучше 5.
Проверка руками занимает много времени и даёт разное качество у разных менторов.

Скилл автоматизирует сбор контекста и подготовку ревью, оставляя за ментором
решение и финальное слово.

## Репозиторий и флоу

- Репозиторий текущего потока: `frontend-park-mail-ru/homework_2026_2`
- 19 веток-вариантов (`variant-1` … `variant-19`), у каждого студента свой вариант
- Студент форкает репозиторий, работает в ветке своего варианта, открывает PR
  в ветку **того же варианта** (не в `master`)
- Ментор ассайнит себя, ставит лейбл «На проверке», ревьюит, по итогу ставит
  «Нужны исправления» либо «ОК от ментора» + assign старшего ментора (`rissenberg`)
- Финальный балл `5/5` ставит старший ментор — скилл этот лейбл не трогает

### Лейблы в репозитории

| Лейбл | Значение | Ставит скилл |
|---|---|---|
| `На проверке` | ДЗ проверяется ментором | да |
| `Нужны исправления` | Студенту нужно поправить замечания | да |
| `ОК от ментора` | Ментор аппрувнул ДЗ (+ assign `rissenberg`) | да |
| `5/5` | ДЗ принято | **нет** |
| `Ошибочный` | Случайный ПР | да |
| `Списано` | ДЗ скачали наглым образом | **нет** |

### Автоматические проверки в репозитории

`.github/workflows/CI.yml` на каждый `pull_request` запускает:

1. `npx eslint --ext .js,.jsx --max-warnings 0 .`
2. `npx karma start` (QUnit в ChromeHeadless)

`.eslintrc.json` расширяет `eslint:recommended` и включает `require-jsdoc` со
`error` для всех видов функций, включая `ArrowFunctionExpression`.

### Файлы, которые запрещено менять

`.github/workflows/CI.yml`, `.eslintrc.json`, `karma.conf.js`, `source/max.js`,
`test/max.js`. Правило зафиксировано в шапке `CI.yml` и в `README.md`.

## Исследование прошлых потоков

Разобрано 2903 ревью-комментария из `homework_2026_1` (70 PR) и
`homework_2024_2` (66 PR). Определены 23 аккаунта менторов (комментировали
≥3 разных PR).

**Частота тем:**

| Тема | Упоминаний |
|---|---|
| `let`/`var` вместо `const` | 322 |
| Нет проверки входных данных | 322 |
| `function` вместо стрелочной | 248 |
| Мало тестов / нет негативных кейсов | 204 |
| `use strict`, `==` vs `===` | 202 |
| Циклы вместо перебирающих методов | 187 |
| Кодстайл (отступы, `;`, кавычки) | 91 |
| Нет пустой строки в конце файла | 88 |
| JSDoc отсутствует или неполный | 79 |
| Упрощение (тернарник, `?.`, `includes`) | 71 |
| Вложенность, декомпозиция, вынос констант | 65 |
| Мутация входных параметров | 17 |
| Гигиена PR (ветка, лишние файлы) | 12 |

**Распределение ревью:** `COMMENTED` — 581, `APPROVED` — 55,
`CHANGES_REQUESTED` — 35. Ревью идёт как итеративный диалог, аппрув только в конце.

**Ключевое наблюдение — сократический стиль.** Менторы почти не пишут «исправь».
Они спрашивают:

> Какие способы объявления переменных есть в JS? В чём между ними разница?
> Почему здесь выбрал `let`?

> За что отвечает директива `use strict`? Что было бы, если бы её не было?

> Можем ли мы заменить цикл на какой-нибудь крутой перебирающий метод?

Скилл обязан воспроизводить этот стиль, иначе он ломает педагогику курса.

## Решения

| Вопрос | Решение |
|---|---|
| Автономия | Черновик в терминал → подтверждение ментора → постинг |
| Формат | Инлайн-комментарии по строкам + сводный комментарий |
| Тон | Сократический, по банку формулировок из прошлых потоков |
| Повторное ревью | Читает тред, не дублирует закрытые замечания |
| Проверка на списывание | **Не входит в объём** |
| Лейблы и ассайн | Входят, по подтверждению |

## Архитектура

Прогрессивное раскрытие: тонкий `SKILL.md` с процессом, справочники грузятся
по необходимости.

```
skills/review-homework/
  SKILL.md              — рабочий процесс, 4 фазы
  references/
    checklist.md        — проверки по приоритетам
    comment-bank.md     — сократические формулировки + ссылки
    variants.md         — 19 вариантов: функция, подводные камни, тест-кейсы
    gh-recipes.md       — команды gh для сбора и постинга
```

При ревью `variant-12` не нужны подводные камни `variant-15` — грузится только
нужная секция.

Репозиторий упакован как плагин Claude Code, поэтому скилл лежит в `skills/` —
именно там Claude Code ищет скиллы плагина. Как это устроено — в
[`plugin-packaging.md`](plugin-packaging.md).

## Рабочий процесс

### Фаза 1 — Сбор (ничего не пишет)

Метаданные PR, список изменённых файлов, diff, статус CI, вариант из базовой
ветки, задание из README ветки варианта, существующие ревью-комментарии и
ответы студента.

### Фаза 2 — Проверки

**Уровень A — блокирующие.** База не `variant-N`; тронуты запрещённые файлы;
маркеры конфликта; лишние файлы в diff; файл переписан целиком из-за смены
line endings; название PR не по формату «WEB-21 Фамилия Имя».
Если сработало — ревью кода не начинаем, просим переоформить PR.

**Уровень B — код.** Проверка входных данных; `'use strict'` первой строкой;
`===`; `const`; стрелочные функции; чистота функции; JSDoc
(`@param`, `@returns`, `@throws`, `@example`, без пустой строки перед функцией);
перебирающие методы вместо циклов; пустая строка в конце файла; вынос
регулярок и магических чисел в константы; вложенность.

**Уровень C — тесты.** Негативные кейсы (`null`, `undefined`, не тот тип),
граничные случаи варианта, осмысленные названия тестов, отсутствие дублей.

### Фаза 3 — Черновик

В терминал: инлайн-заметки (`файл:строка` + текст), сводка, предлагаемый
вердикт и лейбл. **Остановка, ждём ментора.**

### Фаза 4 — Постинг по подтверждению

Одно ревью с инлайн-комментариями через `gh api --input`, затем лейбл и ассайн.

## Границы

Скилл **не** мержит PR, **не** ставит `5/5` и `Списано`, **не** проверяет на
списывание, **не** пушит в ветку студента, **не** постит ничего без явного
подтверждения ментора.
