# Ловушки проверки — план реализации

> **Для агентных исполнителей:** ОБЯЗАТЕЛЬНЫЙ САБ-СКИЛЛ: используйте
> superpowers:subagent-driven-development (рекомендуется) или
> superpowers:executing-plans, чтобы выполнять план задача за задачей.
> Шаги отмечаются чекбоксами (`- [ ]`).

**Цель:** записать в скилл два факта, проверенных прогоном на живых PR, —
ложные совпадения грепа на CRLF-файлах и форму матчера выброса, которая
сверяет и тип, и сообщение.

**Архитектура:** правки только в текстах скилла. Ловушка с грепом — четвёртым
пунктом в список «способов обмануться» в `SKILL.md`, форма матчера и уточнение
про статус находки — в C1 `checklist.md`. Поведение скилла не меняется,
меняется то, что знает агент.

**Технологии:** Markdown, `grep`, `tr`, QUnit 2.26.

**Спека:** [`docs/specs/verification-traps.md`](../specs/verification-traps.md)

## Глобальные ограничения

- Репозиторий скилла публичный: рецепты должны работать не только на машине
  автора. `grep` там может быть GNU, BSD или ugrep.
- Шаблон `^[ \t]\+\r\?$` использовать запрещено: `\t` в скобках понимается
  реализациями по-разному. Отброшен при написании спеки.
- Не подбирать шаблон под перевод строки: на CRLF поведение `$` зависит от
  реализации `grep`. Снимать `\r` до поиска.
- Тексты на русском, обращение к студенту на «ты».
- Утверждать фактом можно только прогнанное — это правило Фазы 2.5, и оно
  распространяется на сами эти правки.

- [ ] **Шаг 4: убедиться, что рецепт из пункта рабочий**

Рецепт попадёт в скилл, поэтому его надо прогнать, а не поверить ему. Сделать
контрольную пару: файл, где искомая строка заведомо есть, и файл, где её нет.

```bash
printf 'a\r\n \r\nb\r\n' > "${TMPDIR:-/tmp}/ctl-yes.txt"
printf 'a\r\nb\r\n'       > "${TMPDIR:-/tmp}/ctl-no.txt"
tr -d '\r' < "${TMPDIR:-/tmp}/ctl-yes.txt" | grep -c '^[[:blank:]]\+$'
tr -d '\r' < "${TMPDIR:-/tmp}/ctl-no.txt"  | grep -c '^[[:blank:]]\+$'
```

править файл под цифру.

### Задача 2: форма матчера и статус находки в C1

**Файлы:**
- Изменить: `skills/review-homework/references/checklist.md`, секция
  `### C1. Негативные кейсы`, последний абзац

**Интерфейсы:**
- Потребляет: ничего.
- Отдаёт: текст, на который ссылается пункт проверки в задаче 3.

- [ ] **Шаг 1: заменить заключительный абзац C1**

Заменить целиком:

```markdown
В обоих живых случаях тест оставался зелёным после удаления проверки, то есть
охранял не её. Как ловить: убери проверку в Фазе 2.5 и посмотри, покраснел ли
тест. Как чинить: матчить сообщение — регуляркой или функцией-предикатом,
которая сверяет и тип, и текст.
```

на:

````markdown
В обоих живых случаях тест оставался зелёным после удаления проверки, то есть
охранял не её.

**Сама по себе форма с конструктором — ещё не находка.** Находкой она
становится тогда, когда тест остаётся зелёным после удаления проверки из
реализации. Если сломанный путь не бросает вовсе, тест краснеет и сторожит
именно проверку студента — заметки нет. Так было на `variant-5`: без guard'а
функция возвращала объект вместо броска, и все пять throw-тестов покраснели.
Поэтому порядок такой: сначала убери проверку в Фазе 2.5, потом решай.

Как чинить, если находка подтвердилась. Самый дешёвый для студента способ —
передать в `assert.throws` **экземпляр** ошибки вместо конструктора:

```js
assert.throws(fn, new TypeError('Аргумент obj должен быть массивом'));
```

QUnit сверяет и тип, и сообщение. Проверено на 2.26.0 контрольной тройкой: тот
же тип с другим текстом падает, другой тип с тем же текстом падает, совпадение
обоих проходит. Регулярка и функция-предикат тоже годятся, но экземпляр писать
проще всего.
````

- [ ] **Шаг 2: проверить результат**

```bash

grep -c 'assert.throws(fn, new TypeError(' skills/review-homework/references/checklist.md
grep -c 'регуляркой или функцией-предикатом,' skills/review-homework/references/checklist.md
```

Ожидается `1`, `1`, `0` — старая формулировка «Как чинить: матчить сообщение —
регуляркой или функцией-предикатом, которая сверяет и тип, и текст» должна
исчезнуть, а упоминание регулярки остаться в новой форме.

Шаблон для второго грепа взят узкий намеренно: голое `new TypeError(`
встречается в C1 уже трижды, в таблице «что бросит JS, если проверку убрать»,
и ничего бы не проверило.

- [ ] **Шаг 3: убедиться, что утверждение про QUnit верно**

Утверждение идёт в скилл как факт, поэтому прогоняется, а не принимается на
веру. Харнесс с установленным QUnit уже лежит в скретчпаде прошлых прогонов;
если его нет — поставить `npm install qunit@2` во временной директории.

```js
const QUnit = require('qunit');
const expected = new TypeError('Аргумент obj должен быть массивом');
QUnit.module('матчер', () => {
  QUnit.test('A тот же тип и текст', (assert) => {
    assert.throws(() => { throw new TypeError('Аргумент obj должен быть массивом'); }, expected);
  });
  QUnit.test('B тот же тип, другой текст', (assert) => {
    assert.throws(() => { throw new TypeError('другое'); }, expected);
  });
  QUnit.test('C другой тип, тот же текст', (assert) => {
    assert.throws(() => { throw new RangeError('Аргумент obj должен быть массивом'); }, expected);
  });
});
QUnit.on('testEnd', (t) => console.log(t.name, t.status));
QUnit.start();
```

Ожидается: `A passed`, `B failed`, `C failed`. Если B проходит — утверждение
про сверку сообщения неверно, и об этом надо сообщить, а не править текст под
ожидание.
