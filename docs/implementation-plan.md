````markdown
# Ревью домашки по фронтенду

Готовит ментору черновик ревью студенческого PR и постит его только после подтверждения.

## Когда применять

Ментор просит проверить PR в `frontend-park-mail-ru/homework_2026_2`
(или в репозитории другого потока — `homework_2026_1`, `homework_2024_2`).
Обычно звучит как «отревьюй PR 4», «проверь домашку Иванова», «глянь мои PR».

## Железные правила

1. **Ничего не постится в GitHub без явного подтверждения ментора.** Фазы 1–3
   только читают и печатают в терминал.
2. **Никогда не ставить лейблы `5/5` и `Списано`.** Финальный балл — за старшим
   ментором, списывание — не наша зона.
3. **Никогда не пушить в ветку студента и не мержить PR.**
4. **Тон — сократический.** Мы спрашиваем, а не приказываем. Студент должен
   понять почему, а не просто применить патч. Формулировки — из
   `references/comment-bank.md`.
5. **Один блокирующий уровень за раз.** Если PR оформлен неправильно (не та
   базовая ветка, тронуты запрещённые файлы) — не ревьюим код, просим
   переоформить.

## Фаза 1 — Сбор контекста

Ничего не пишет. Команды — в `references/gh-recipes.md`, секция «Сбор».

Собрать:

- Метаданные PR: номер, заголовок, автор, `baseRefName`, `headRefName`, лейблы, ассайны
- Список изменённых файлов с числом добавлений и удалений
- Полный diff
- Статус CI (`eslint --max-warnings 0` и `karma`); при падении — лог упавшего шага
- Номер варианта из базовой ветки → задание из README этой ветки
- **Существующие ревью-комментарии и ответы студента** — обязательно, иначе
  повторное ревью будет дублировать закрытые замечания

Определить, первое это ревью или повторное: если в PR уже есть комментарии от
менторов, это повторное.

## Фаза 2 — Проверки

Читать `references/checklist.md` целиком и `references/variants.md` — только
секцию нужного варианта.

Три уровня в строгом порядке:

- **A. Блокирующие** — оформление PR. Если хоть один сработал, уровни B и C
  пропускаем: код ревьюить бессмысленно, пока diff показывает не то.
- **B. Код** — реализация функции.
- **C. Тесты** — дописанные студентом тесты.

При повторном ревью для каждого прошлого замечания определить: исправлено /
не исправлено / студент ответил вопросом. Не поднимать заново то, что закрыто.

## Фаза 3 — Черновик в терминал

Напечатать ментору:

1. **Шапка** — PR, автор, вариант, задание одной строкой, статус CI, какое это ревью по счёту
2. **Блокирующие проблемы** — если есть
3. **Инлайн-заметки** — каждая в формате `путь/файл.js:строка` + текст комментария
4. **Сводный комментарий** — то, что уйдёт в тело ревью
5. **Предлагаемый вердикт** — `COMMENT` / `APPROVE` и лейбл
6. **Что скилл сделает после подтверждения** — списком

Затем **остановиться и ждать**. Не постить, не спрашивать «продолжать?» в той же
реплике, где печатается черновик — ментор должен успеть прочитать и поправить.

## Фаза 4 — Постинг

Только после явного «да, постим» (или после правок ментора).

Порядок — в `references/gh-recipes.md`, секция «Постинг»:

1. Ассайн ментора на PR, если он ещё не ассайнен
2. Одно ревью с инлайн-комментариями через `gh api --input`
3. Лейблы: снять неактуальные, поставить нужный
4. При вердикте «ОК от ментора» — дополнительно assign `DPeshkoff`

После — напечатать ссылку на PR и что именно поставлено.
````

````markdown
# Рецепты gh

Везде `R` — репозиторий потока, `N` — номер PR.

```bash

## Сбор

### Метаданные PR

```bash
gh pr view N -R $R --json number,title,author,baseRefName,headRefName,labels,assignees,isCrossRepository,changedFiles,additions,deletions,url
```

`baseRefName` даёт вариант. `isCrossRepository: true` — норма, студенты форкают.

### Изменённые файлы

```bash
gh api "repos/$R/pulls/N/files" -q '.[] | .filename + "  +" + (.additions|tostring) + " -" + (.deletions|tostring)'
```

Красный флаг: у файла число удалений примерно равно числу строк файла, а
добавлений — чуть больше. Значит файл переписан целиком, обычно из-за смены
переносов строк (CRLF ↔ LF). Проверка — в `checklist.md`, пункт A5.

### Diff

```bash
gh pr diff N -R $R
```

### Статус CI

```bash
gh pr checks N -R $R
```

Если печатает `no checks reported` — workflow не запускался (частый случай на
форках, где Actions не включены). Это не вина студента, но стоит упомянуть в
сводке: автопроверки не прогонялись, значит `eslint` и тесты нужно
просмотреть глазами внимательнее.

При падении — лог упавшего шага:

```bash
gh run list -R $R --branch <headRefName> --limit 3 --json databaseId,conclusion,headSha
gh run view <databaseId> -R $R --log-failed
```

### Задание варианта

```bash
gh api "repos/$R/contents/README.md?ref=variant-12" -q '.content' | base64 -d | sed -n '/#### Задание/,/### Файлы/p'
```

### Существующие комментарии

Обязательно перед повторным ревью.

```bash
gh api "repos/$R/pulls/N/comments" -q '.[] | "[\(.user.login)] \(.path):\(.line // .original_line)\n\(.body)\n---"'
gh api "repos/$R/issues/N/comments" -q '.[] | "[\(.user.login)]\n\(.body)\n---"'
gh pr view N -R $R --json reviews -q '.reviews[] | "\(.author.login): \(.state)"'
```

### Ревью с инлайн-комментариями

Собрать payload в файл — так надёжнее, чем передавать вложенные объекты флагами.
Писать во временную директорию, не в репозиторий.

```bash
cat > "$TMPDIR/review.json" <<'JSON'
{
  "body": "Привет! Посмотрел решение. В целом хорошо, оставил несколько вопросов и замечаний — глянь, пожалуйста.",
  "event": "COMMENT",
  "comments": [
    {
      "path": "source/flatten.js",
      "line": 13,
      "side": "RIGHT",
      "body": "Что произойдёт, если в функцию передать не массив — например, `null` или строку? Давай добавим проверку входных данных и тесты на неё."
    }
  ]
}
JSON

gh api "repos/$R/pulls/N/reviews" --method POST --input "$TMPDIR/review.json"
```

Правила по `line`:

- `line` — номер строки в **новой** версии файла, `side` всегда `RIGHT`
- Строка обязана присутствовать в diff, иначе API вернёт `422`
- Для комментария к удалённой строке — `side: "LEFT"`
- Для диапазона — добавить `start_line` и `start_side`

`event` держать `COMMENT`, пока есть замечания. `APPROVE` — только когда
замечаний не осталось. `REQUEST_CHANGES` в этом курсе менторы почти не
используют, роль «нужны правки» играет лейбл.

Если API вернул `422 Unprocessable Entity` — почти всегда строка вне diff.
Найти ближайшую изменённую строку и перепривязать комментарий.

### Лейблы

Ставить ровно один статусный лейбл, предыдущий снимать.

```bash
# взял в работу
gh pr edit N -R $R --add-label "На проверке"

# отправил замечания
gh pr edit N -R $R --remove-label "На проверке" --add-label "Нужны исправления"

# всё хорошо, передаём старшему ментору
gh pr edit N -R $R --remove-label "Нужны исправления" --remove-label "На проверке" --add-label "ОК от ментора"
gh pr edit N -R $R --add-assignee DPeshkoff

# случайный PR
gh pr edit N -R $R --add-label "Ошибочный"
```

Лейблы `5/5` и `Списано` не ставим никогда.

### Просто комментарий без ревью

```bash
gh pr comment N -R $R --body "текст"
```
````

````markdown
# Чек-лист проверок

Три уровня. Если сработал хоть один пункт уровня A — уровни B и C пропускаем.

## A. Блокирующие — оформление PR

### A1. Ветки

`baseRefName` обязан быть `variant-N` — веткой варианта студента.
`headRefName` обязан быть той же веткой варианта (или веткой, отведённой от неё).

Две разные поломки:

- **`baseRefName: "master"`** — PR нацелен в мастер. В прошлом потоке 10 PR
  получили лейбл `Ошибочный` именно из-за этого. В diff видны сотни изменений
  или содержимое чужих вариантов.
- **`headRefName: "master"`** — студент форкнул мастер и работал в нём, не
  переключившись на ветку своего варианта. Тогда в diff попадает вся разница
  между мастером и веткой варианта: служебные файлы, `README.md`, `index.html`.

Действие: просим переоформить PR — ветка варианта в ветку того же варианта.
Ревью кода не начинаем.

### A2. Название PR

Формат — «WEB-21 Фамилия Имя» (номер группы, фамилия, имя). Допустимо с номером
варианта. Недопустимо: «first try», «Implement flatten», «Mr variant 2»,
«Написал функционал flatten для прохождения тестов».

### A3. Запрещённые файлы

В diff не должно быть: `.github/workflows/CI.yml`, `.eslintrc.json`,
`karma.conf.js`, `source/max.js`, `test/max.js`.

Запрет прописан в шапке `CI.yml` и в `README.md`.

### A4. Лишние файлы

В diff должно быть ровно два файла: `source/<функция>.js` и `test/<функция>.js`.
Лишнее: `index.html`, `README.md`, `.gitignore`, `package.json`, `.idea/`,
`.vscode/`, `node_modules/`, `screenshot.png`.

### A5. Файл переписан целиком

Признак: у файла удалений примерно столько же, сколько в нём было строк, а
добавлений чуть больше — при том что по смыслу студент добавил пару тестов.

Причина почти всегда — смена переносов строк (CRLF ↔ LF) или замена отступов.
Из-за этого ревьюеру не видно настоящих изменений.

Пример из живого PR: `test/flatten.js  +42 -19` при трёх добавленных тестах —
файл пересохранён с другими переносами строк.

Действие: просим настроить редактор и перезалить, сохранив исходные переносы.

### A6. Маркеры конфликта

В diff есть `<<<<<<<`, `=======`, `>>>>>>>`.

## B. Код

### B1. Проверка входных данных

Самая частая содержательная претензия. Функция обязана переживать `null`,
`undefined`, не тот тип. Способ на выбор студента: бросить ошибку, вернуть
`null`, вернуть пустое значение — лишь бы кейс был обработан осознанно и
задокументирован в JSDoc.

### B2. `'use strict'`

Первой строкой файла. Проверять и в `source/`, и в `test/`.

### B3. Строгие сравнения

`===` и `!==` вместо `==` и `!=`. Отдельно: избыточные проверки вида
`=== false`, `=== undefined` там, где хватит `!value` — но осторожно с falsy,
если по условию важны `0`, `false` и пустая строка.

### B4. `const` по умолчанию

`let` только там, где переменная действительно переприсваивается. `var` — не
использовать. Функция объявляется через `const`.

### B5. Стрелочные функции

Вместо `function declaration` и `function expression`.

**Исключение — `variant-16` (`fibonacciGenerator`).** Генератор объявляется
через `function*`, стрелочным он быть не может. Не требовать переписать.

### B6. Чистота функции

Входные параметры не мутируются. Классические ловушки: `sort()` и `reverse()`
мутируют массив — нужен `[...array].sort()`. В рекурсивных слияниях объектов
вложенные объекты часто протекают по ссылке.

### B7. JSDoc

Требуется у **каждой** функции — это правило `require-jsdoc` в `.eslintrc.json`
со `severity: error`, включая `ArrowFunctionExpression`. Без него падает CI.

Должно быть: описание, `@param` с типом на каждый параметр, `@returns`,
`@throws` если функция бросает, `@example` желательно, `@async` для
асинхронных.

Между JSDoc и функцией **не должно быть пустой строки** — иначе комментарий не
привязывается. Частая причина падения CI.

Типы — из JSDoc, не из TypeScript: `Object.<string, *>`, а не `Record<string, any>`.

### B8. Перебирающие методы вместо циклов

`map`, `filter`, `reduce`, `forEach`, `some`, `every`, `find`, `flatMap`,
`Object.keys/values/entries` вместо `for`, `for...of`, `while`.

Отдельно: если студент накапливает результат во внешнюю переменную — это
`reduce`. Менторы подсвечивают `reduce` специально, студенты его избегают.

Обратное тоже верно: если ничего не накапливается, `reduce` неуместен, лучше
`forEach` или `map`.

### B9. Пустая строка в конце файла

### B10. Константы

Регулярные выражения выносить за пределы функции в именованную константу —
создаётся один раз, и по имени понятно, что она проверяет. Магические числа —
в константы в `UPPER_SNAKE_CASE`.

### B11. Читаемость

Вложенность больше двух уровней — просим декомпозировать: ранние `return`,
вынос в отдельную функцию. Тело `if` и циклов — всегда в фигурных скобках.
````

````markdown
`source`); `typeof null === 'object'` ломает рекурсию; массивы — по условию не
сливаются рекурсивно, но это стоит отразить в JSDoc.

Тесты: приоритет второго объекта при конфликте, глубокая вложенность, `null` в
значениях, исходники не изменились после вызова.

## variant-3 — compressObject

Возвращает новый объект без ключей со значениями `null`, `undefined` и пустой
строки.

Подводные камни: проверка через `if (!value)` вместо трёх конкретных значений —
**`0` и `false` тоже отсеются, а не должны**; мутация исходного объекта.

Тесты: значения `0` и `false` сохраняются, все три отсеиваемых значения,
пустой объект, вложенные объекты.

## variant-4 — factorial

Неотрицательное целое `n` → факториал.

Подводные камни: нет проверки на отрицательное, дробное и не-число; `0! = 1`
забыт; рекурсия без ограничения глубины; потеря точности на больших `n`.

Тесты: `0`, `1`, отрицательное (выброс ошибки), дробное, строка, `null`,
большое значение.

## variant-5 — deepClone

Глубокая копия объекта.

Подводные камни: **циклические ссылки** — без `WeakMap` уходит в бесконечную
рекурсию; `Date`, `Map`, `Set`, `RegExp` копируются неправильно; массивы
превращаются в объекты; `typeof null === 'object'`.

Тесты: вложенность, массивы, `Date`, `null`, циклическая ссылка, объект без
прототипа, изменение копии не трогает оригинал.

## variant-6 — filterByKeys

Объект и массив ключей → новый объект только с этими ключами. Отсутствующий
ключ игнорируется.

Подводные камни: значения-объекты копируются по ссылке — по условию их нельзя
изменять; не проверено, что `keys` вообще массив; `hasOwnProperty` против
унаследованных свойств.

Тесты: ключа нет в объекте, пустой массив ключей, `null` вместо объекта,
вложенный объект не мутируется.

## variant-7 — transform

Объект и функция преобразования. Функция применяется к каждому значению,
вложенные объекты обрабатываются рекурсивно.

Подводные камни: мутация исходного объекта; не проверено, что `transformFn` —
функция; массивы внутри объекта.

Тесты: вложенность, `transformFn` не функция, пустой объект, исходник не
изменился.

## variant-8 — plainify

Объект с вложенными свойствами → plain-объект.

Подводные камни: **рекурсивная функция объявлена внутри `plainify`** и
пересоздаётся при каждом вызове — менторы это ловят; служебные параметры
рекурсии торчат наружу в сигнатуре; формат составного ключа не задокументирован.

Тесты: глубокая вложенность, пустой объект, массивы, `null`.

## variant-9 — groupBy

Массив объектов и ключ → объект, где ключи это уникальные значения поля.

Подводные камни: цикл вместо `reduce`; объекты без нужного ключа не обработаны;
не проверено, что первый аргумент массив, а второй строка.

Тесты: ключа нет в части объектов, пустой массив, одинаковые значения ключа,
невалидные аргументы.

## variant-10 — mergeBy

Два массива объектов и ключ. Объекты с одинаковым значением ключа сливаются,
массивы-свойства объединяются без дубликатов.

Подводные камни: `includes` внутри цикла даёт **O(n²)** — лучше `Set`;
мутация входных массивов; объекты, у которых ключа нет.

Тесты: объекты с одинаковым ключом внутри одного массива, слияние
массивов-свойств с дубликатами, пустые массивы.

## variant-11 — partition

Массив и предикат → массив из двух массивов.

Подводные камни: два отдельных массива и `push` вместо `reduce`; не проверено,
что `predicate` функция; предикат вызывается дважды на элемент.

Тесты: все элементы проходят, ни один не проходит, пустой массив, предикат не
функция.

## variant-12 — flatten

Вложенный массив любой глубины → плоский.

Подводные камни: нет проверки, что аргумент массив — падает на `null`;
рекурсия без ограничения; пустые вложенные массивы.

Тесты: глубокая вложенность, пустые вложенные массивы, элементы разных типов,
не-массив на входе, исходник не изменился.

## variant-13 — emailAnalyzer

Строка → `{ emailCount, uniqueEmails, mostFrequentEmail }`. Регистр
игнорируется.

Подводные камни: **регулярка внутри функции** — надо вынести в константу
модуля; регистр не приводится к нижнему; `mostFrequentEmail` через цикл вместо
`reduce`; пустая строка и отсутствие адресов.

Тесты: пустая строка, адресов нет, разный регистр одного адреса, одинаковая
частота у нескольких адресов, не строка на входе.

## variant-14 — templateEngine

Шаблон и объект данных. `{{user.name}}` — вложенные переменные. Ненайденная
переменная → пустая строка.

Подводные камни: регулярка не вынесена в константу; колбэк `replace` не
стрелочный; вложенный путь не разбирается; пробелы внутри `{{ ключ }}`;
значение `0` или `false` теряется из-за проверки на falsy.

Тесты: переменной нет в данных, вложенный путь, пустой шаблон, значение `0`,
не строка на входе.

## variant-15 — polishNotationEvaluator

Строка в префиксной нотации → результат. Операторы `+`, `-`, `*`, `/`.

Подводные камни: деление на ноль; невалидное выражение не обрабатывается;
унарный минус в операндах; лишние пробелы; операторы не вынесены в константу.

Тесты: все четыре оператора, вложенные выражения, деление на ноль, невалидное
выражение, пустая строка, отрицательные операнды.

## variant-16 — fibonacciGenerator

Число `n` → генератор первых `n` чисел Фибоначчи. При `n <= 0` не выдаёт ничего.

Подводные камни: **не требовать стрелочную функцию** — генератор объявляется
только через `function*`; возвращается массив вместо генератора; `n <= 0` не
обработано; JSDoc не отражает, что возвращается `Generator`.

Тесты: `n = 0`, отрицательное `n`, `n = 1`, первые несколько чисел, что
возвращается именно генератор (`typeof result.next === 'function'`),
не-число на входе.

## variant-17 — sortByFrequency

Массив чисел → отсортированный по частоте. При равной частоте — по возрастанию.

Подводные камни: **`sort()` мутирует входной массив** — нужен `[...array].sort()`;
частоты считаются циклом вместо `reduce`; второй критерий сортировки забыт.

Тесты: одинаковая частота у разных чисел, пустой массив, все элементы
уникальны, исходный массив не изменился, отрицательные числа.

## variant-18 — findUniqueProperties

Два объекта → объект только с уникальными для каждого свойствами.

Подводные камни: цикл вместо `Object.keys` + `filter`/`reduce`; не проверено,
что оба аргумента объекты; вложенные объекты.

Тесты: полностью совпадающие объекты, полностью разные, пустой объект, `null`
вместо объекта.

## variant-19 — sortByLength

Массив строк → отсортированный по длине. При равной длине — по алфавиту.

Подводные камни: **`sort()` мутирует входной массив** — нужен spread;
алфавитный порядок через `>` вместо `localeCompare`; не проверено, что элементы
строки.

Тесты: строки одинаковой длины, пустой массив, пустые строки, кириллица,
исходный массив не изменился.
````
